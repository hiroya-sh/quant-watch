## 日本語要約
561 commits の大型リリース。**FlashAttention 4 (SM100) が FP8 KV cache と headdim-256 をサポート**し、Kimi K3(compressed-tensors 量子化 checkpoint 含むフルスタック)対応、Qwen3.5 dense/MoE 追加。量子化面では **FP4 Qutlass 統合(compressed-tensors)、ReLU2 NVFP4 の CuTeDSL MoE、INC の MXFP8 linear、DeepSeek-V4/Kimi-K3 の compressed-tensors checkpoint** など多数。DeepSeek-V4 は MXFP4 indexer KV cache などで性能改善。

## 量子化関連の変更点
- 新規対応手法/フォーマット: FP4 Qutlass (compressed-tensors, #43229), NVFP4 CuTeDSL MoE (#49580), MXFP8 linear in INC (#47514), FlashAttention4 FP8 KV cache (#42569)
- 既存手法の改善: Quark w8a8-int8 (#46765) / MXFP4, MoeWNA16 の MK oracle 移行
- 対応モデル拡張: DeepSeek-V4 / Kimi-K3 の compressed-tensors checkpoint, Gemma-4 ViT CUDA graph

## 影響範囲
- ユーザ視点の変化: Blackwell SM100 で FP8 KV cache が FA4 経路で使える。DeepSeek-V4/Kimi-K3 の量子化 checkpoint を直接 serving 可能
- API/CLI 変更の有無: PyTorch 2.13 への破壊的環境更新、FusedMoE→FusedMoEFactory 改名

## 注目度コメント
focus の NVFP4・moe-quant に合致し vllm-ready 付与。FP8 KV cache が FA4 native で乗った点は KV 量子化評価の実行環境として最重要。

## 1. 前回（0.26.0）の理解の整理 — 「カーネルが更新されて低bit圧縮が動く」の中身

Hiroyaさんが受けた報告の実体は、**compressed-tensors 経由で「2の冪でない任意ビット幅」の weight-only モデルが vLLM で直接動くようになった**こと。

> v0.26.0 Quantization セクション:
> *"Humming w[2-7]a[4,8] weight-only inference with compressed-tensors (#46390); int4 quantization for the emulation MoE backend (#48451); INT2 XPU weight-only quant linear (#47521)."*

つまり w2/w3/w5/w6/w7 のような中間ビット幅が「変換すれば載る」状態になった。加えて `nvfp4_per_token` により **チェックポイントを作らずにオンラインで MoE を NVFP4 化**できるようになり、実験の初期コストが下がった。これは全部 **重み側**の話で、長文を流したときの KV メモリには効かない。

### 2.1 ★最重要: FlashAttention 4 が SM100 で FP8 KV cache を native サポート (#42569)

**何ができるか**: Blackwell (SM100) で、KV キャッシュを FP8(e4m3) で保持したまま **FA4 カーネル内で直接読んで attention を計算**できる。従来 Blackwell で FP8 KV を使うなら FlashInfer 系に寄せる必要があった（下記ブログ参照）。これで FA4 の速さと FP8 KV のメモリ節約を同時に取れる。

**起動方法**（PR 本文記載のフラグ）:

```
vllm serve <model> --attention-backend FLASH_ATTN --kv-cache-dtype fp8 --max-model-len 8192
```

**精度の実測**（PR #42569、Nemotron 3 Nano 30B / GSM8K）:

| backend | GSM8K |
|---|---|
| FlashInfer | 94.31% |
| **FA4** | **95.22%** |

→ FA4 経路にしても精度は落ちない（むしろ僅かに上）ことを示した上でのマージ。

**制約**（PR 本文ママ）: 実装は SM100 限定。長文での精度は上流 FlashAttention リポジトリの修正に依存する、と明記されている。

### 2.2 「何が効率的になったのか」— FP8 KV cache が効く理屈と実測

FP8 KV の効き方は vLLM 公式ブログ (2026-04-22) の測定が一次情報として一番具体的。0.27.0 は**その恩恵を FA4 backend でも受けられるようにした**という位置づけ。

| 指標 | BF16 KV → FP8 KV |
|---|---|
| KV キャッシュのメモリ | **半減（-50%）** |
| デコードの ITL（トークン間レイテンシ）の傾き | BF16 の **54–71%** |
| 負荷時の出力スループット | **+4.8〜14.9%**（モデル構造依存） |
| 精度（reasoning、無校正） | 劣化 1〜2 point（**97〜99% recovery**） |
| 精度（long-context、最大 1M tok） | baseline AUC の **94〜98%** |
| 損得の分岐点 | **約 7k tokens**（Llama 級）。それ以下は BF16 が有利 |

> ブログ原文:
> *"KV-cache memory reduced by 50%"*, *"Decode inter-token latency (ITL) slope reduced to 54-71% of BF16"*, *"Break-even points at ~7k tokens for Llama-class models"*

### 2.3 FA4 headdim-256 対応 (#42669) — ただし期待しすぎ禁止

head_dim=256 は上のブログで「**FP8 KV の弱点**」として挙がっていた箇所（two-level accumulation により prefill が約 1.6 倍遅くなる）。0.27.0 で FA4 が headdim 256 を扱えるようになった。ただし PR 本文は自ら限界を明記している。

> PR #42669 原文:
> *"This kernel only supports `block_size = tile_n = 128` at this head size, which precludes its use for mamba models like Gemma 3."*
> *"This kernel is currently slower than `TRTLLM_RAGGED`."*

→ 実際にはこのサイズでは **`TRTLLM_RAGGED` を優先するようルーティングを調整**している。**Gemma 系 / mamba 系では block_size 制約で使えない**点は、Mamba/GLA 周りをやっている進行中プロジェクトに直接刺さるので注意。

### 2.4 MXFP4 indexer KV cache の詰め直し (#48993) — 地味だが一番「効率化」らしい変更

DeepSeek-V4 の sparse attention indexer 用 K 行を、FP8 想定の大きめ確保から**実際のパック値＋スケール分だけ**に right-size。さらに cache group を共有スラブに密に重ね置き。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| indexer K 1行（128 dim） | 132 B | **68 B** |
| block stride（FlashInfer sparse） | 1,308,672 B | 1,228,800 B（**-6.1%**） |
| block stride（FlashMLA sparse） | 1,473,408 B | 1,315,008 B（**-10.75%**） |
| GB200 で確保できるブロック数 | — | **+6.5〜12%** |

> PR #48993 原文（要旨）: allocate indexer K rows by *"their actual packed values and scales"* rather than the larger FP8 row size, reducing a 128-dim row *"from 132 to 68 bytes"*.

「量子化フォーマットを増やす」話ではなく、**既に量子化した物のレイアウトの無駄を削る**話。同じ GPU で 6〜12% 多く並列に載る、という素直な効率化。

### 2.5 重み側の追加分（0.26 の続き）

- **FP4 Qutlass integration (#43229)**: compressed-tensors に CUTLASS ベースの FP4 GEMM 経路（`QutlassNvFP4LinearMethod`）。入力側に **Hadamard 正規化**（Had16 / Had128 のブロックサイズ）を噛ませてから FP4 GEMM に落とす構成で、flashinfer の scaled FP4 と統合。Llama 3 8B のベンチは出力スループット 9,416〜9,794 tok/s、TTFT 平均 498〜567ms（構成別）。
  - ⚠️ **要確認**: リリースノートには 0.27.0 の成果として載っているが、PR ページ自体は Draft 表示に見えた。実際に何が 0.27.0 に入ったかは `vllm.model_executor.layers.quantization` 配下の実装を pip 版で確認するのが確実。
- **CuTeDSL MoE for ReLU2 NVFP4 (#49580)**: NVFP4 の MoE 経路を CuTeDSL カーネルで。0.26 の MXFP4 CuTe-DSL に続く NVFP4 版。
- **MXFP8 linear support in INC (#47514)** / **AutoRound W4A16 MoE + MXFP4 linear/MoE on XPU (#47124)**: Intel 系（INC / XPU）の低精度線形層の拡充。
- **ModelOpt FP8 emulation on SM80 (#50019)**: A100 世代でも FP8 を**エミュレーションで**動かせる（速くはならないが、Blackwell を待たずに数値挙動の検証ができる）。
- **compressed-tensors support for DeepSeek-V4 (#41276) / Kimi-K3 (#50500)**: 公開されている量子化 checkpoint を**変換なしでそのまま serve** できる。

### 2.6 ★見落とし注意: TurboQuant の KV quant mode (#50533)

focus method の **TurboQuant が vLLM の `--kv-cache-dtype` プリセットとして既に存在している**。0.27.0 に入ったのは、`auto` に上書きされてしまい起動できなかったバグの修正。

> PR #50533 の再現コマンド（原文ママ）:
> ```
> vllm serve Qwen/Qwen3-30B-A3B-Thinking-2507 --kv-cache-dtype turboquant_4bit_nc
> ```
> エラー: *"Unknown TurboQuant cache dtype: 'auto'"*

利用可能なプリセット（PR 本文記載）:

| プリセット | 想定 |
|---|---|
| `turboquant_k8v4` | K を 8bit、V を 4bit |
| `turboquant_4bit_nc` | K/V ともに 4bit（no-calibration） |
| `turboquant_k3v4_nc` | K 3bit / V 4bit（no-calibration） |
| `turboquant_3bit_nc` | K/V ともに 3bit（no-calibration） |

対象は Model Runner V2 (mrv2) の KV cache 初期化と TurboQuant attention backend。**校正不要（nc）で 3〜4bit KV が CLI 一発で試せる**ので、focus の kv-cache-quant 評価の入口として最短。

> ⚠️ 週次レポート W34 の「今週なしカテゴリ」で *methods TurboQuant: 該当なし* と書かれているが、本リリースに #50533 が含まれるため**実際は該当あり**。routine 側の抽出漏れ（リリースノート内の focus method 語彙のスキャン漏れ）。

## 3. 「何が壊れるか」— 破壊的変更

> リリースノート原文:
> *"Removed the no-longer-supported `max_num_partial_prefills` and `max_long_partial_prefills` arguments"*
> PyTorch は 2.13.0（torchvision 0.28.0 / Triton 3.7.1）へ。

- **PyTorch 2.13.0 必須**: `nvidia-modelopt` / `flash-linear-attention` / `mamba-ssm` / `causal-conv1d` を使っている進行中プロジェクトの環境と衝突しうる。**先に別 venv で 0.27.0 を立てるのが安全**。
- **`FusedMoE` → `FusedMoEFactory` 改名 (#44941)**: 自前で FusedMoE を import しているコードは修正が必要。
- **`MoeWNA16` が MK oracle 方式へ移行 (#44120)**: WNA16 MoE のカーネル選択ロジックが変わるため、性能が前バージョンと変わる可能性。

## 4. Hiroyaさん視点での「今すぐ試せること」

1. **FP8 KV の素性確認（Blackwell 前提）**
   `--attention-backend FLASH_ATTN --kv-cache-dtype fp8` で、7k 以上の長文プロンプトを流して ITL 傾きとメモリを BF16 と比較。ブログ値（傾き 0.54〜0.71、メモリ -50%）が自環境で再現するかが基準線。
2. **TurboQuant 3/4bit KV の校正なし評価**
   `--kv-cache-dtype turboquant_k3v4_nc` 等で focus の TurboQuant を直接比較。**FP8 KV(2倍) vs TurboQuant 3bit(約5倍) のメモリ/精度カーブ**を引くのが一番情報量が多い。
3. **Gemma-4 は headdim 256 の block_size 制約に注意**（#42669）。FA4 経路が使えないケースは `TRTLLM_RAGGED` にフォールバックされる前提で測る。
4. **A100 しか空いていない場合**: `ModelOpt FP8 emulation on SM80` (#50019) で数値挙動だけ先に検証（速度は測れない）。

## 5. 0.26.0 → 0.27.0 早見表

| 観点 | v0.26.0 (07-27) | v0.27.0 (08-10) |
|---|---|---|
| 圧縮する対象 | **重み**（w2-7 任意ビット、INT2、オンライン NVFP4 MoE） | **KV キャッシュ / attention 実行**（FP8 KV native、MXFP4 indexer、TurboQuant KV） |
| 効く場面 | モデルのロード VRAM、デコード帯域 | 同時並列数、最大文脈長、長文の ITL |
| 代表的な数値 | 非2冪ビット幅が「動く」ようになった（機能解禁） | KV -50%、ITL 傾き 0.54–0.71、throughput +4.8〜14.9%、indexer 行 132B→68B |
| 前提ハード | 汎用（XPU/ROCm 含む） | **SM100 (Blackwell) 前提の機能が中心** |
| 環境影響 | — | **PyTorch 2.13.0 必須**、FusedMoE 改名 |
